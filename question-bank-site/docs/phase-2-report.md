## 1. المشكلة قبل التنفيذ

الموقع كان يحفظ نوعين من البيانات فقط:

| المفتاح | المحتوى | المشكلة |
|---|---|---|
| `qb.best` | أفضل نسبة لكل مقرر | رقم واحد، بلا تاريخ |
| `qb.review.v1` | أسئلة تحتاج مراجعة | **يُحذف منها** السؤال بعد إجابتين صحيحتين |

`qb.review.v1` سجل مؤقت الغرض منه «ماذا أراجع الآن»، وليس «ماذا فعلت». السؤال الذي أُجيب صحيحًا مرتين **يُمحى من الوجود** — فتضيع بيانات المحاولة تمامًا. هذا هو الفصل الذي طالبت به الخارطة في §3.3.

النتيجة: لم يكن ممكنًا الإجابة على أسئلة مثل «كم سؤالًا حللت هذا الأسبوع؟» أو «هل تحسّنت؟» أو «أي قسم أضعف؟».

## 2. سجل المحاولات

### البنية

```jsonc
{
  "v": 1,
  "attempts": [                       // كل إجابة، بلا استثناء
    { "id": "ethics-mcq-5f93..",      // معرّف السؤال
      "t": 1794337957504,             // وقت المحاولة (ms)
      "o": "correct",                 // correct | wrong | revealed
      "a": 2,                         // الخيار المختار (-1 = إظهار الإجابة)
      "c": "ethics", "s": "mcq" }     // المقرر والقسم
  ],
  "sessions": [                       // كل جلسة حل
    { "id": "smwb2hrs", "start": 1794.., "end": 1794..,
      "mode": "exam", "courseId": "acct", "courseTitle": "...",
      "isReview": false, "finished": true, "timedOut": false,
      "total": 48, "answered": 48, "correct": 36, "wrong": 12,
      "revealed": 0, "pct": 75 }
  ],
  "streak": { "current": 3, "best": 7, "lastDay": "2026-11-10" }
}
```

### القرارات التصميمية

**1. فصل تام عن سجل الأخطاء**
`qb.review.v1` بقي كما هو بلا أي تعديل — نفس المنطق ونفس المفاتيح، فلا حدث ترحيل ولا خطر على بيانات مستخدمة موجودة. السجل الجديد مستقل تمامًا.

**2. السجل يُكتب أولًا**
```js
function recordAttempt(q, answer, course){
  recordHistoryAttempt(q, answer, course);   // audit trail first: never missed
  updateHistorySession();
  // ... ثم منطق سجل الأخطاء القديم كما هو
}
```
كل نقاط التسجيل الخمس في الموقع تمر عبر `recordAttempt`، فأصبحت نقطة عبور واحدة للسجل الجديد. لا يوجد مسار يكتب في سجل الأخطاء ويفوت السجل.

**3. ثلاث نتائج لا نتيجتان**
`revealed` منفصل عن `wrong`. حين يضغط الطالب «إظهار الإجابة» لم يخطئ ولم يصب — هذا سلوك مختلف تعليميًا، وإدماجه في «خطأ» يشوّه نسبة الدقة.

**4. تخزين محدود بنيويًا**
`localStorage` له حد صارم (~5 MB لكل نطاق)، وسجل غير محدود يملأه ثم **يفشل بصمت** عند التجاوز — فيضيع كل شيء دون تحذير. لذلك:

| الحد | القيمة | السبب |
|---|---|---|
| `HISTORY_MAX_ENTRIES` | 5000 محاولة | أقدم المحاولات تُسقط |
| `HISTORY_MAX_AGE_DAYS` | 400 يوم | تنقية عمرية عند الكتابة |
| `sessions` | 400 جلسة | كافية لأكثر من سنة |

**5. السجل يتحمل الفساد**
`loadHistory()` يتحقق من الشكل ويعيد بنية سليمة عند أي تلف، بدلًا من رمي استثناء يعطّل الصفحة. مغطّى باختبار.

### حجم التخزين الفعلي

محاولة واحدة ≈ 85 بايت. 5000 محاولة ≈ **425 KB** — أقل من 10% من حد `localStorage`.

## 3. لوحة التحليلات

شاشة جديدة (`state.view === 'analytics'`) تُفتح من زر **«التحليلات»** في الشريط العلوي، بأربعة تبويبات.

### التبويب 1 — نظرة عامة

- أربع بطاقات: إجمالي المحاولات، نسبة الصحيحة، عدد الأسئلة المختلفة، سلسلة الأيام المتتالية.
- **رسم بياني لآخر 14 يومًا**: عمود لكل يوم، ارتفاعه بعدد المحاولات، والجزء الأخضر منه نسبة الصحيحة.
- توزيع الإجابات: صحيحة / خاطئة / تم إظهار الإجابة.
- بطاقة «أسئلة لم تجرّبها بعد» مع زر لحل 100 سؤال جديد.

### التبويب 2 — المقررات

الأداء لكل مقرر ولكل قسم، مرتّبًا من الأفضل إلى الأقل، مع شريط ملوّن (أخضر ≥70%، برتقالي ≥50%، أحمر <50%).

### التبويب 3 — نقاط الضعف

| ما تعرضه | القاعدة |
|---|---|
| أضعف الأقسام | ترتيب تصاعدي بالدقة، **بحد أدنى 3 محاولات** |
| أقوى الأقسام | ترتيب تنازلي بالدقة، نفس الحد |
| أسئلة أخطأت فيها أكثر | ترتيب بعدد الأخطاء + الإظهار، مع نص السؤال كاملًا |

الحد الأدنى 3 محاولات مقصود: قسم بمحاولة واحدة خاطئة ليس «أضعف الأقسام» — عرضه بثقة كاذبة. الاختبارات تتحقق من استبعاد ما تحت الحد.

زر **«تدرّب على أضعف 5 أقسام»** يبني اختبارًا فوريًا من تلك الأقسام.

### التبويب 4 — المحاولات

قائمة آخر 40 جلسة: النوع (امتحان/تدريب/مراجعة)، التاريخ، الوقت، وما إذا كانت مكتملة أو متروكة أو انتهى وقتها. الجلسات غير المكتملة تعرض نسبة الإنجاز (`12/30`) بدلًا من درجة.

### قاعدة الحساب

كل رقم في الشاشة مشتق من `attempts` الخام عبر `computeAnalytics()` — لا يوجد عدّاد مخزّن منفصل يمكن أن ينتج «رقمًا لا يطابق الواقع». الاختبارات تتحقق من الحساب رياضياً (3 صحيحة + 1 خاطئة من 4 = 75%)، لا من وجود النص فقط.

### التحقق أن الاختبارات ليست شكلية

ست طفرات متعمّدة، كلها مكتشفة:

| الكسر المتعمّد | النتيجة |
|---|---|
| السجل لا يسجّل شيئًا | ✗ **12** اختبارًا فشل |
| الدقة تُحسب على أساس خاطئ | ✗ اختبار فشل |
| الجلسات لا تُحدَّث | ✗ اختبار فشل |
| نقاط الضعف بلا ترتيب | ✗ اختبار فشل |
| إلغاء حد الـ 3 محاولات | ✗ اختبار فشل |
| إلغاء سقف الـ 5000 | ✗ اختبار فشل |

> **اكتشاف أثناء العمل:** أول تشغيل أظهر نسبة دقة **0%** مع 5 محاولات مسجّلة. بدا كخطأ في الحساب، لكن التحقق أثبت أن `q0.ans = 3` بينما الاختبار ينقر الخيار 0 — أي أن الحساب صحيح والبيانات المتوقعة في الاختبار كانت خاطئة. تغطي الاختبارات النهائية الحالتين معًا (صحيحة وخاطئة) لتفادي هذا اللبس.

> **اكتشاف ثانٍ:** الجلسة كانت تُفتح بـ `answered: 0` ولا تُحدَّث أثناء الحل — تعديل واحد (`updateHistorySession()` داخل `recordAttempt`) أصلحها، وكُتب اختبار يمنع رجوعها.

## 5. الوصول والأمان

- كل تبويب `role="tab"` مع `aria-selected`.
- الحاوية `role="tablist"` مع `aria-label`.
- **كل نص سؤال في شاشة نقاط الضعف يمر عبر `esc()`** — أُضيف اختبار يتحقق أن `<img onerror>` لا ينفّذ.
- الألوان لا تحمل المعنى وحدها: كل شريط يعرض النسبة رقمًا بجانبه.

## 7. ما لم يُنفَّذ ولماذا

### Spaced Repetition (§3.1)

الخارطة تقترح جدول مراجعة متدرجًا (خطأ → قريب، صحيح بصعوبة → يوم، إتقان → أسبوع...). السجل الحالي يجعل هذا **قابلًا للتنفيذ** لأنه يحفظ وقت كل محاولة ونتيجتها، فيمكن حساب مستوى الإتقان لكل سؤال.

لكن التنفيذ يحتاج قرارًا في التصميم: هل يُستبدل سجل الأخطاء الحالي (إجابتان صحيحتان = إزالة) بالنظام الجديد، أم يُضاف نظامان متوازيان؟ الإضافة المتوازية تعني زرّين مختلفين للمراجعة وأنواعًا مختلفة من «الأسئلة المستحقة» — وهذا يعقّد الواجهة. أنصح بانتظار قرارك قبل البناء.

### Bookmarks و Search

مستقلتان تقنيًا وأسهل ما تبقى. Search يحتاج العناية بأداء الفلترة على 709 أسئلة داخل المتصفح (مباشر، لكن يستحق قياسًا).

## 9. الخطوة التالية

المرشّحون بالترتيب:

1. **Bookmarks + Search** — مستقلان، منخفضا الخطورة، قيمة مباشرة.
2. **Spaced Repetition** — يحتاج قرارك في التصميم أولًا (§7).
3. **Export / Import** — يحمي بيانات الطالب من ضياع `localStorage`، ويصبح ذا معنى الآن بعد أن صار السجل ثمينًا.
